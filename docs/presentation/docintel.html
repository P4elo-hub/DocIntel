Почему здесь нужен ИИ

Это не поиск страницы, а работа с документацией

Понять вопрос

Аналитик спрашивает человеческим языком, а в документах живут названия API, поля и внутренние термины.

Без ИИ

Поиск требует угадать точные слова из документа: имя обмена, поле JSON, системное сокращение.

В DocIntel

Запрос переводится в смысловой поиск: модель связывает пользовательскую формулировку с нужным разделом базы знаний.

ИИ нужен как переводчик между вопросом и языком документации.

Собрать ответ

Полезный ответ часто лежит не в одном абзаце: назначение, контракт, пример и ограничения разнесены по разделам.

Без ИИ

Пользователь получает список ссылок и сам сравнивает несколько страниц, таблиц и примеров.

В DocIntel

RAG достаёт фрагменты, а агент собирает из них ответ или черновик фичи по шаблону.

ИИ нужен как сборщик связного ответа из найденных источников.

Удержать границы

Если в базе нет факта, ассистент должен отказаться или показать пробел, а не придумать контракт.

Без ИИ

Обычный поиск не различает: найден точный источник, похожий документ или вообще соседняя тема.

В DocIntel

Классификатор отделяет рабочие запросы от off-topic, ответ строится с цитатами, validate-агент перепроверяет по свежему поиску.

ИИ нужен как контролёр: отвечать только там, где есть опора на базу.

03 / 13

База знаний

В индекс попадает рабочая документация

Выбрано

Основной корпус — актуальные markdown-документы проекта: описание функций, сценарии, API-контракты, ограничения, словарь терминов и справочная схема данных.

Рассматривалось

Индексировать всё подряд: архивные страницы, черновики, автосводки, полные выгрузки БД и учебный sample-корпус.

Почему отказ

Шумные источники ухудшают ответы: архив даёт устаревшие правила, черновики дублируют факты, сырые таблицы раздувают индекс без бизнес-смысла. Учебные данные хранятся отдельно, чтобы не смешивать оценку и рабочую базу.

Выбор моделей

Не одна модель на всё, а роли в пайплайне

Модель выбиралась не «самая большая», а подходящая под задачу: быстро направить запрос, найти источники и собрать ответ без выдумывания.

Агенты

gpt-4o-mini, температура 0. Используется для classify, search, answer/write и validate: быстрые шаги, tool calling, предсказуемые ответы.

Синтез ответа

gpt-5.4-mini, температура 0. Отдельная модель для RAG-ответа: собрать несколько найденных фрагментов в связный ответ с цитатами.

Поиск

text-embedding-3-small → Qdrant, затем bge-reranker-v2-m3. Реранкер включён по умолчанию: он проверяет, какие чанки действительно отвечают на вопрос.

От чего отказались

  • Одна большая модель везде — дороже, а routing и validate не требуют максимальной модели.
  • Одна и та же модель для агентов и RAG — смешивает короткие tool-шаги и длинный синтез ответа.
  • Поиск без реранкера — быстрее, но чаще поднимает похожий чанк вместо точного.

Рекомендация

  • Оставить текущий split: агенты, синтез, embeddings отдельно.
  • Реранкер держать включённым; для стабильного запуска нужен HF-кэш и замер latency.
  • Локальный Ollama llama3.2:3b оставить только как проверку fallback; железо и SLO под него не считать.

Хранение и поиск

Как система выбирает правильный фрагмент

Поиск устроен в два шага: сначала быстро найти кандидатов, потом реранкером проверить, какой чанк действительно отвечает на вопрос.

Markdownстраницы KB
→
Чанкипо заголовкам
→
Qdrantdense + BM25
→
Реранкерпроверяет вопрос ↔ чанк
→
LLMответ с цитатами

Где лежат знания

Qdrant хранит векторы и метаданные чанков. Postgres остаётся для истории чата, поэтому диалоги и база знаний не смешиваются.

Как режем документы

Чанк — раздел markdown: до 1024 токенов, overlap 128. Так таблицы контрактов и примеры не разваливаются на отдельные предложения.

Зачем реранкер

Qdrant даёт похожие кандидаты. Реранкер включён по умолчанию и выбирает из них точные: он сравнивает сам вопрос с текстом чанка.

Агентный слой

Граф ролей вместо одного большого агента

Каждый агент делает одну работу. Поэтому видно, где был поиск, где написание, а где проверка ответа.

Пользовательвопрос, поиск или документ
→
valid inputguard до агентов
→
classifyвыбирает сценарий
→
answersearch_kb → короткий ответ → validate
→
writesearch_kb → kit-агенты по секциям → validate
⇢
rejectчужая тема или нет опоры в KB

Текущая версия

Сначала validate_input, затем LangGraph с явным state: answer, write и пунктирный reject.

Что пробовали

v1: простой RAG + LLM. v2: один ReAct с search_kb и write_feature_doc. v3: граф ролей — текущий вариант.

Почему не один агент

ReAct был чуть быстрее, но смешивал поиск, черновик и проверку. В графе validate заново читает KB и не верит тексту, который только что написал write.

Поведение при сбоях

Лучше честный отказ, чем тихая подмена ответа

Fallback используется только там, где он не ломает доверие к ответу. Если система не может опереться на KB, она говорит об этом явно.

1. Повторяем

  • Временная ошибка модели — до 3 попыток.
  • Rate limit, auth и moderation не ретраятся.
  • Пустой ответ агента — отдельная ошибка, не молчание.

2. Деградируем

  • Если реранкер недоступен, можно временно остаться на dense/BM25.
  • Локальный Ollama проверяет fallback простого клиента.
  • Но агентный граф не заменяется тихо на слабую модель.

3. Отказываем

  • Score ниже 0,3 — «в базе нет ответа».
  • Prompt injection / DAN / base64-like ввод — 400 до агентов.
  • Qdrant недоступен — поиск не притворяется успешным.
  • Без OpenAI embeddings новый поиск не строится.

Правило

Если fallback ухудшает достоверность контрактов или документа фичи, пользователь видит понятную ошибку вместо «примерно похожего» ответа.

Контроль качества

Система не просто отвечает — она знает, когда нельзя

Главный принцип: лучше честно отказать, чем уверенно придумать контракт. Это уже встроено в пайплайн.

Безопасный вход

  • Prompt injection режется до LLM.
  • Чужая тема уходит в reject.
  • Вредный или слишком шумный ввод не попадает к агентам.

Ответ только по KB

  • Qdrant находит кандидатов.
  • Реранкер выбирает правильный чанк.
  • Если источника нет — система говорит «не нашёл».

Проверка результата

  • Validate заново читает KB.
  • Write не проверяет сам себя.
  • Длинный документ собирается по секциям.

Дальше усиливаем

Точнее резать большие разделы, добавлять метаданные к чанкам, включить чекпоинты и human-in-the-loop для длинных документов. Это roadmap улучшения качества, а не blocker для демо.

Итог

DocIntel превращает базу знаний в рабочий инструмент аналитика

Система не просто генерирует текст: она ищет источники, выбирает релевантные фрагменты, собирает ответ или документ и проверяет границы допустимого.

Что сделано

Telegram/web-ассистент для поиска, ответов по контрактам, черновиков фичи и честного reject вне темы.

Как достигнуто

Qdrant + реранкер находят нужные чанки, LangGraph разделяет роли, validate заново сверяет результат с KB.

На чём держится

Разные модели под разные роли, guard до LLM, ответы с источниками и отказ там, где нет опоры на базу.

Итог: меньше ручного поиска по документации, меньше риска выдуманного контракта, быстрее подготовка черновика.
